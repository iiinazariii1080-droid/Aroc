# Safety Envelope & Workspace Constraints (V3 add-on)

Дата: 2026-01-28

Цель: гарантировать, что **любой** скрипт/endpoint/teleop работает *только* внутри ограниченной рабочей зоны и
манипулятор **не выходит за габариты** (включая «локти» / звенья), обеспечивая плавность и предсказуемую безопасность.

---

## 1) Определения и единицы

- Все значения ниже задаются в **миллиметрах** (mm), если не указано иное.
- **Workspace Box (WS)** — прямоугольный параллелепипед 40×90×120 cm:
  - `WS.size = (X=400, Y=900, Z=1200) mm`
- **WS origin** — один выбранный «угол» зоны (например, левый‑передний‑нижний). Важно лишь, чтобы это было фиксировано и измеримо.
- **Robot base** находится внутри WS в точке:
  - `base_in_ws = (X=150, Y=450, Z=0) mm`  *(15×45×0 cm)*

> Принцип: сначала формализуем **кадры координат**, затем любые пределы/границы вычисляются автоматически из этих трансформаций.

---

## 2) Frames: WS → Base → TCP

Минимальный набор кадров:

- `ws` — кадр рабочей зоны (box‑frame).
- `base` — базовый кадр манипулятора (xArm base).
- `tcp` — кадр инструмента/фланца.

Нужно определить фиксированное преобразование `T_ws_base`:
- если оси WS параллельны осям base, достаточно `translation = base_in_ws` и `rotation = identity`;
- если манипулятор установлен с поворотом/наклоном относительно зоны — нужно задать `rotation` (yaw/pitch/roll) или матрицу/кватернион.

### Рекомендуемая практика калибровки
1) Выберите **физический ноль WS** (угол зоны), пометьте его.
2) Измерьте 3 точки (origin, +X, +Y) и восстановите ориентацию WS.
3) Сохраните `T_ws_base` в конфиге и версионируйте.

---

## 3) Жёсткое ограничение на контроллере xArm (hardware-level)

Используйте **Reduced/Safety Boundary Mode** на контроллере:
- `set_reduced_tcp_boundary([x_max, x_min, y_max, y_min, z_max, z_min])`
- `set_reduced_mode(True)`

### Как вычислить boundary в base‑frame из WS
Если `T_ws_base` — только перенос (оси совпадают), то границы WS относительно base:

```
x_min_base = 0 - base_in_ws.x  = -150
x_max_base = 400 - base_in_ws.x =  250
y_min_base = 0 - base_in_ws.y  = -450
y_max_base = 900 - base_in_ws.y =  450
z_min_base = 0 - base_in_ws.z  =    0
z_max_base = 1200 - base_in_ws.z = 1200
```

Добавьте **safety margin** (например 30–50 mm) и зажмите границы внутрь:
- `x_min += margin`, `x_max -= margin`, и т.д.

> Важно: hardware boundary обычно гарантирует минимум для TCP (и/или режима безопасности контроллера). Это **первая линия защиты**, но не единственная.

---

## 4) Программное ограничение «локти внутри зоны» (software-level, MUST)

Требование: не только TCP, но и **все звенья/суставы** не выходят за пределы WS.

### Компоненты
- `RobotModel` (URDF + кинематика) — умеет считать FK для **всех** звеньев.
- `SafetyEnvelope` — проверяет, что геометрия робота (capsules/boxes) целиком внутри WS.
- `TrajectoryValidator` — дискретизирует траекторию и прогоняет через `SafetyEnvelope`.

### Представление геометрии
Практичный вариант без тяжёлого collision engine:
- каждое звено аппроксимируем **capsule** (отрезок + радиус),
- проверяем capsule‑в‑box с margin (или дискретизацией по точкам вдоль отрезка).

Если у вас уже есть/планируется MoveIt2/Pinocchio/FCL:
- используйте полноценную проверку коллизий/ограничений.

### Правило выполнения (инвариант)
Любая команда движения в `RobotActor` проходит:
1) `preflight_validate(command)`:
   - FK для целевой позы/джоинтов
   - проверка WS для всех звеньев
   - проверка self‑collision (если доступно)
2) `trajectory_validate(command)`:
   - построение траектории (линейной/джоинт)
   - дискретизация N точек
   - envelope check для каждой точки
3) только после этого — фактический вызов SDK.

---

## 5) Runtime guard (вторая линия защиты)

Даже после preflight:
- связь/энкодеры могут глючить,
- кто-то вмешался в режим,
- фактическая траектория может отличаться.

Поэтому нужен `SafetyMonitor`:
- частота 20–50 Hz
- читает текущие joint angles / tcp pose
- рассчитывает FK по текущим углам
- если обнаружена граница/опасная зона:
  - **soft stop** (если возможно) → затем **hard stop**
  - переводит систему в `FAULTED`, блокируя дальнейшие команды до explicit recovery.

---

## 6) Плавность (smoothness) — motion policy

Плавность достигается не “побольше задержек”, а политикой движения:

- Единый конфиг лимитов: max TCP speed/acc/jerk, max joint speed/acc.
- В teleop/servo режимах — фильтр (low‑pass) + ограничение jerk.
- Для pick&place — предпочтительно:
  - joint move к безопасной «высокой» промежуточной позе
  - затем линейный подход к цели
  - линейный отход
- Запрет резких смен направления: blending/radius (если поддерживается контроллером) или траектория через точки.

---

## 7) Конфиг (пример)

```yaml
workspace:
  size_mm: [400, 900, 1200]
  base_in_ws_mm: [150, 450, 0]
  margin_mm: 40
  frame:
    ws_to_base:
      translation_mm: [150, 450, 0]
      rotation_rpy_deg: [0, 0, 0]

safety:
  enable_reduced_mode: true
  enable_sw_envelope: true
  monitor_rate_hz: 30
  stop_policy: "soft_then_hard"
  soft_zone_margin_mm: 80

motion_limits:
  tcp_speed_mm_s: 150
  tcp_acc_mm_s2: 800
  tcp_jerk_mm_s3: 4000
  joint_speed_deg_s: 40
  joint_acc_deg_s2: 150
```

---

## 8) Acceptance Criteria (DoD)

- Любая команда движения отклоняется, если траектория выводит **любой линк** за WS.
- Hardware boundary сконфигурирован и проверен (reduced mode).
- Runtime guard гарантированно останавливает при нарушении.
- Есть тесты:
  - unit: envelope math
  - integration: validator + actor
  - hardware smoke: движение к 6 границам WS на минимальных скоростях
